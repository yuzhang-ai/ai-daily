# AI 每日简报

**读者**：关注 AI 行业的公开读者，包括产品经理、开发者、创业者。日报不是作者的私人笔记，正文不出现「你」「我的项目」「作品集」「面试」「求职」这类话。

**所有命令都在仓库根目录运行。** 日期一律用北京时间，下文 `DATE` 指当天，例如 `2026-11-11`。

## 1. 采集

```bash
python3 -I skill/ai-daily/scripts/collect.py
```

脚本会写出 `work/candidates-DATE.md`，读这个文件。

- 先看「信源状态」，把失败的信源记下来。超过一半失败时脚本会以非 0 退出：先排查网络，不要凭记忆写。
- 周一或节后可以加 `--hours 72`，把周末也纳入。
- 候选池的排序只反映被多少来源报道，不代表值得写。

## 2. 初筛

先读 `references/selection.md`，然后对候选池逐条过一遍：

1. 排除第四节列出的噪声类型。
2. 合并脚本没合并上的同一事件。同一产品的发布、定价、接入某平台、HN 讨论都算一件事。
3. 对剩下的事件按五项打分，只保留 6 分及以上的。
4. 标「近 7 天已写」的事件，只有出现新的实质信息才再写。

把结果写进 `work/triage-DATE.md`，一行一个事件：`事件 | 分数 | 要闻 / 快讯 / 淘汰 | 一句理由`。维护者靠这张表复查选题。

## 3. 核实

对每条要闻和快讯，打开一手来源（官方博客、文档、论文、仓库）读全文：

- 价格、基准分数、参数量、日期这些数字，只用一手来源里出现的。橘鸦、Latent Space 和各家媒体只用来发现线索。
- 一手来源打不开时，用两家独立的可信媒体交叉核对。两家都找不到，就把这条降为快讯或者放弃，并在 triage 表里写明原因。
- 开源项目用 GitHub API 查 star 数、许可证和创建时间：`curl -s https://api.github.com/repos/OWNER/REPO`。
- 记下发布日期。超出采集窗口的事件不算今天的新闻。

## 4. 写作

按 `references/template.md` 写 `outputs/AI-Daily-DATE.md`。

- 用第三人称、陈述句。读者不需要读过前几期也能看懂。
- 「为什么重要」要讲清改变了什么：之前怎样，现在怎样。
- 「核心观点」写 3 条，每条带一个具体事实（数字、名称或机制）。
- 「这意味着什么」写对行业、产品或开发者的影响。可以下判断，但判断要能从前面的事实推出来。
- 「风险与待验证」写厂商自测、未经独立验证、仅预览、只限部分地区或套餐等情况。
- 不用「最强」「炸裂」「王炸」「颠覆」，改用数字和对比。厂商自称第一时，写成「Google 称……排名第一」。
- 中英文混排时，英文和数字两边各加一个空格。

## 5. 自检

```bash
grep -nE '作品集|面试|求职|我的项目|对你' outputs/AI-Daily-DATE.md
```

```bash
python3 -I site/build.py site/dist
```

- 第一条命令应该没有输出。
- 第二条命令必须构建成功，且输出的期数比上次多 1。
- 每个数字都能在对应的来源链接里找到。
- 3 条要闻来自不同的公司。例外只有一种：两件事互不相关，且都在 8 分以上。

## 6. 提交

```bash
git add outputs/AI-Daily-DATE.md && git commit -m "AI Daily DATE" && git push
```

推送到 `main` 之后，GitHub Actions 会自动构建并发布网站。只提交 `outputs/` 下的新文件，`work/` 不进仓库。

## 什么时候少写或不发

- 采集失败超过一半：不发，向维护者报告是哪些信源失败。
- 达标的要闻不到 3 条：只写达标的条数，不凑数，并在「今日一句话」里如实说明当天比较平静。

## 维护

- 信源列表在 `scripts/collect.py` 的 `SOURCES` 里。某个信源连续 3 天失败，就修它的解析逻辑或者删掉它。
- 选题标准在 `references/selection.md`。每个季度按该文件第八节的方法，用产品君最近的周报复核一次。
