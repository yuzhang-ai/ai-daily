## 一、今日最值得关注的 3 条内容

### 1. Anthropic: Effective context engineering for AI agents
- 来源链接：[Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- 类型：博客
- 推荐指数：5 星
- 一句话总结：Agent 能力的关键不再是把 prompt 写长，而是把有限 context window 当成稀缺预算，动态装入最有信号的信息。
- 为什么重要：这篇把 `Context Engineering` 讲成了可执行工程框架：system prompt、tools、examples、message history、runtime retrieval、compaction、structured note-taking、sub-agent architecture 都是 context 预算分配问题。对 AI 产品经理 / FDE 来说，这比“多写提示词”更接近真实交付：客户现场的数据、工具、日志、文档、历史决策都很多，产品价值来自让 Agent 在合适时间看到合适信息。
- 核心观点 3 条：
  1. Context 是有限注意力预算，不是越多越好；信息过载会带来 `context rot` 和注意力稀释。
  2. Agentic search 应该更多使用 `just-in-time context`：先保留文件路径、查询、链接等轻量索引，需要时再通过工具加载。
  3. 长周期任务需要 compaction、结构化笔记和 sub-agent 分工，而不是指望一个超长对话一直撑到底。
- 对 AI 产品经理 / FDE 的启发：做 Agent 产品时，PRD 里要单独写“context contract”：哪些信息默认进上下文，哪些通过工具按需取，哪些只进入记忆，哪些必须隔离。
- 可落地行动或作品集切入点：做一个“客户成功 Agent context 设计稿”：把客户资料、历史会议、CRM、工单、产品文档、SOP 拆成 upfront context / runtime retrieval / memory / forbidden data 四类，并设计失败时的人工复核。
- 风险提醒：不要把长上下文当万能方案；对客户数据、密钥、内部文档要做最小可见范围和脱敏。该文为长网页，需上线阅读全文。
- 是否值得精读：是。

### 2. Anthropic: Writing effective tools for agents — with agents
- 来源链接：[Anthropic Engineering](https://www.anthropic.com/engineering/writing-tools-for-agents)
- 类型：博客
- 推荐指数：5 星
- 一句话总结：Agent 工具不是传统 API 的简单包装，而是“确定性系统”和“非确定性 Agent”之间的新型协作界面。
- 为什么重要：很多 Agent 项目失败不是模型不够强，而是工具设计让模型迷路：工具太多、功能重叠、返回信息太脏、错误提示不可行动、评估任务过于玩具化。Anthropic 给出的方向很适合 FDE：先做真实任务 eval，再让 Agent 阅读 trace，反过来优化工具 schema、描述、返回结构和 token 成本。
- 核心观点 3 条：
  1. 工具要服务 Agent 的任务分解方式，不要机械复制后端接口；例如 `search_logs` 往往比 `read_logs` 更适合 Agent。
  2. 工具返回应高信号、低 token、语义清晰；必要时提供 `concise / detailed` 等响应格式，让 Agent 控制信息量。
  3. Tool eval 要基于真实复杂任务，记录准确率、调用次数、运行时间、token 消耗、工具错误和 trace，而不是只看单次 demo。
- 对 AI 产品经理 / FDE 的启发：FDE 的壁垒会从“会接 API”升级为“会把客户系统重构成 Agent-friendly tools”。这本质是产品架构能力：定义能力边界、默认返回、失败反馈和验证指标。
- 可落地行动或作品集切入点：选一个业务场景，如招聘、客户跟进、工单排查，设计 5 个 Agent tool：每个写清工具名、用途、输入输出、错误提示、权限、token 控制和对应 eval case。
- 风险提醒：工具越强，权限风险越大；写入、删除、批量发送、外部网络访问必须有人审或有沙箱。该文为长网页，需上线阅读全文。
- 是否值得精读：是。

### 3. Anthropic: How we contain Claude across products
- 来源链接：[Anthropic Engineering](https://www.anthropic.com/engineering/how-we-contain-claude)
- 类型：博客
- 推荐指数：5 星
- 一句话总结：高能力 Agent 的安全不是“多弹确认框”，而是用 sandbox、VM、文件边界、egress control 等硬边界限制 blast radius。
- 为什么重要：这篇非常适合建立 Agent 产品安全观。Anthropic 明确说，人类逐步会产生 approval fatigue，Claude Code 用户大约 93% 的权限提示都会批准；因此只靠 human-in-the-loop 不够。真正可靠的是环境层 containment：让 Agent 技术上无法碰到不该碰的文件、网络和凭证。
- 核心观点 3 条：
  1. Agent 风险来自 user misuse、model misbehavior、external attackers 三类，防御要覆盖 environment、model、external content 三层。
  2. 不同产品需要不同隔离：claude.ai 用 ephemeral container，Claude Code 用开发者可理解的 OS sandbox，Claude Cowork 面向非技术用户更适合本地 VM。
  3. Egress allowlist 不是简单的“允许访问某域名”，而是 capability grant；被允许的域名内部每个能力都可能成为外泄通道。
- 对 AI 产品经理 / FDE 的启发：企业 Agent 方案不能只写“人工确认”。更专业的交付方案应该包含权限矩阵、运行环境、网络出口、日志审计、客户数据边界和异常回滚。
- 可落地行动或作品集切入点：做一页“Agent 安全产品方案”：以客户资料分析 Agent 为例，画出 workspace mount、read-only CRM、no external egress、write action approval、日志留存、密钥不进沙箱。
- 风险提醒：不要在真实业务环境复现实验性 prompt injection 或 exfiltration；分享时只讲防护原则，不传播可直接滥用的攻击细节。该文为长网页，需上线阅读全文。
- 是否值得精读：是。

## 二、今日最重要的一个观点

> 今天我最应该记住的是：Agent 产品的核心竞争力正在从“会回答”转向“能在受控环境里长期做事”。Context 决定它看见什么，Tools 决定它能做什么，Containment 决定它绝对不能做什么。好的 AI PM / FDE 不是堆 prompt，而是把这三件事设计成可验证、可复用、可交付的工作流。

## 三、值得深入学习的开源项目

### 1. addyosmani/agent-skills
- GitHub 链接：[addyosmani/agent-skills](https://github.com/addyosmani/agent-skills)
- Star 数：约 70,233
- 解决什么问题：把 senior engineer 的工作流、质量门禁、最佳实践打包成 AI coding agents 可调用的 skills 和 slash commands，覆盖 spec、plan、build、test、review、ship。
- 为什么值得我学习：它把“AI 协作经验”沉淀成可安装、可迁移、可验证的流程资产，和你想做的 AI PM / FDE 作品集非常贴近。
- 如何用到我的项目 / 工作中：可以仿照它做一套“AI 产品经理 Agent Skills”：需求访谈、PRD、竞品分析、数据埋点、实验设计、上线清单、复盘模板。

### 2. pbakaus/impeccable
- GitHub 链接：[pbakaus/impeccable](https://github.com/pbakaus/impeccable)
- Star 数：约 43,802
- 解决什么问题：给 AI coding agents 增加前端设计约束，包含 1 个 skill、23 个 commands、浏览器迭代和 45 条确定性 UI 检测规则。
- 为什么值得我学习：作品集最容易输在“看起来像 AI 随手生成”。Impeccable 的价值是把 taste、设计上下文、反模式检测、UI polish 变成可重复流程。
- 如何用到我的项目 / 工作中：给你的每个 AI 作品集项目增加 `PRODUCT.md` / `DESIGN.md` / UI 验收清单，避免卡片堆叠、紫蓝渐变、空洞 hero、移动端溢出等常见 AI UI 痕迹。

### 3. walkinglabs/learn-harness-engineering
- GitHub 链接：[walkinglabs/learn-harness-engineering](https://github.com/walkinglabs/learn-harness-engineering)
- Star 数：约 9,892
- 解决什么问题：从 0 到 1 学习 Harness Engineering，把 Agent 外围的脚手架、流程、上下文、验证和运行环境系统化。
- 为什么值得我学习：你近期关注 Harness / Loop Engineering，这个方向正好把“模型调用”升级成“可长期运行、可调试、可验证的 AI 工作系统”。
- 如何用到我的项目 / 工作中：用它作为学习路线，把一个作品集项目拆成 agent loop、tools、memory、eval、human review、observability 六个模块来建设。
