# AI Daily 2026-07-10

## One-liner

> The next stage for agents is not "better at answering" but "better at being orchestrated, evaluated and delivered". The moat for AI PMs and FDEs lies in organizing models, tools, context, cost, verification and human decisions into a reusable software factory.

## Top stories

### 1. OpenAI: GPT-5.6 and Programmatic Tool Calling, pushing agents from "calling tools" to "orchestrating tools"

- Sources: [OpenAI blog](https://openai.com/index/gpt-5-6/); [Programmatic Tool Calling docs](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling)
- Type: Official blog / Developer docs
- Rating: 5 stars
- Summary: The focus of GPT-5.6 is not only model scores but more efficient tool-heavy workflows, a parallel multi-agent beta, and a tool-calling paradigm in which the model writes lightweight programs to process intermediate results.

**Why it matters:** The most valuable part of this for AI product managers and FDEs is not "another stronger model" but that it puts the cost, speed and controllability of agent products on the same table. OpenAI emphasizes GPT-5.6's efficiency gains in coding agents, terminal workflows, long-horizon engineering and knowledge work, and positions `Programmatic Tool Calling` as the key capability for reducing model round trips, filtering intermediate data and orchestrating tool flows. In other words, competition among agent products will increasingly look like a "workflow operating system": which steps the model thinks through, which steps a program filters, which steps run in parallel, and which steps must go back to a human.

**Key points:**
1. Tool use is upgrading from "the model calls one function" to "the model generates and executes lightweight programs to coordinate tools, process intermediate results and decide the next step".
2. Parallel multi-agent is not just showing off; it trades higher cost for shorter latency and higher task success, suited to high-value, long-chain, verifiable tasks.
3. Benchmarks in a model release should not be read only for the top score, but also for tokens, time, cost, number of tool calls and failure recovery.

**What it means:** When designing an agent solution, write `tool orchestration` into the product design rather than only "integrate MCP / API". A mature PRD should state: how large tool returns are, which intermediate results need compression, which computations need not go back to the model, how parallel agents divide work, what the cost ceiling is, and how to degrade after failure. When facing customers, an FDE should also be able to explain why the same task can be split into a combination of "model judgment + program processing + human confirmation".

**Risks and open questions:** Programmatic Tool Calling raises the agent's autonomous processing capability and also raises execution complexity. Any tool call that involves writing to systems, sending information out, customer data, funds, contracts or account permissions must keep a human gate, logging and a rollback strategy. ### 2. Anthropic / Claude: LG CNS uses Claude Code to migrate a 20-year legacy system; the software factory is becoming a real delivery form

- Sources: [LG CNS Claude Code case study](https://claude.com/customers/lg-cns)
- Type: Official customer case / Enterprise agent engineering
- Rating: 5 stars
- Summary: LG CNS put Claude Code into an engineering orchestration layer, completed 2,888 of 2,913 API conversions and the migration of 1,340 front-end pages, and compressed the modernization of a large legacy system to 7 months at about 50% of the cost of a traditional rebuild.

**Why it matters:** This is not a demo of "letting AI write code" but an enterprise-grade migration system: legacy analysis, business logic extraction, code generation, testing, verification and quality management are chained into a pipeline. Most importantly, LG CNS did not treat Claude as an all-purpose black box; it built a thin but multi-layer harness: tasks are broken into small pieces with YAML, stage artifacts are written to local files, files serve as the context handoff, and engineers own direction, decomposition, verification and the quality bar.

**Key points:**
1. The value of enterprise agents is not replacing engineers line by line but turning projects that could not start because of cost, risk or scarce experts into executable roadmaps.
2. Context length is not a silver bullet; what really matters is context taxonomy, stage artifacts, consistent output formats, task boundaries and verification strategy.
3. A good harness is not necessarily thicker; over-constraining the model increases token consumption and suppresses its problem-solving ability. The key is lightweight verification, clear scope and quality checks.

**What it means:** What customers really care about is: how the old system is analyzed, how business logic is extracted, how tasks are decomposed, how outputs are handed off, how tests prove correctness, how quality is unified, and at which points humans make the call.

**Risks and open questions:** The official case is a customer success story; ROI, cost and completion rate need to be understood within the real project's boundaries and cannot be extrapolated directly to all systems. When customer source code, databases and migration documents are involved, pay attention to permissions, redaction, log retention and compliance approval. ### 3. RuBench: Evaluating coding agents with Russian customer-style requests, a reminder that "the evaluation target is the product configuration, not just the model"

- Sources: [arXiv abstract](https://arxiv.org/abs/2607.06411); [PDF](https://arxiv.org/pdf/2607.06411); [GitHub](https://github.com/eugeneshilow/rubench)
- Type: Paper / Open source benchmark
- Rating: 5 stars
- Summary: RuBench uses 25 real open-source repository fix tasks, Russian-native customer-style requests and private maintainer regression tests to evaluate "product configurations" such as Claude Code and Codex CLI, and finds that some configurations undergo model substitution.

**Why it matters:** Yesterday we already looked at agent evals and the quality flywheel; RuBench today adds a sharper question: when what users actually use is `CLI agent + model + reasoning effort + default tools/harness`, are we testing the model or the product? The paper writes tasks as Russian customer requests rather than translating from English issues, avoiding testing only the English GitHub issue pattern; tasks come from fix commits new in 2026, reducing training contamination; grading uses withheld regression tests rather than an LLM judge. It is realistic for FDEs: customers do not always raise requests as standard English issues; they describe problems in business language, with messy symptoms and implicit acceptance criteria.

**Key points:**
1. Repository-level coding agent benchmarks need to cover real customer language, real repositories and real tests, not just standard English issues.
2. Evaluation should record the product configuration and the trajectory, because the CLI, tools, default policies and reasoning effort all affect results.
3. Small-sample benchmarks can still be valuable, but they must honestly report uncertainty, repeated runs, cost, tokens, failure trajectories and statistical bounds.

**What it means:** When evaluating enterprise agents, do not write the test set as "standard questions the model is best at reading". Use what customers actually say: colloquial language, Chinese, abbreviations, business exceptions, system errors, historical baggage. And do not just write "model A beats model B"; record in which tool environment, with which permissions, which prompt, which context, which version and at what cost it is better.

**Risks and open questions:** RuBench has only 25 tasks and cannot serve as a general leaderboard; Russian tasks also cannot directly represent Chinese, English or private enterprise scenarios. What is most worth learning is the evaluation design, not the absolute scores. The PDF was downloaded and verified as a PDF file of reasonable size.

## Open source worth a look

1. Project: eugeneshilow/rubench
   GitHub: [https://github.com/eugeneshilow/rubench](https://github.com/eugeneshilow/rubench)
   Stars: 2 (new project, as shown on the GitHub page)
   What it solves: provides a repository-level agentic coding benchmark with Russian-native customer-style tasks, public task metadata, full agent trajectories, final diffs, a harness and a withheld oracle manifest.
   Why it's worth a look: it is a good template for "how to design a real agent eval". The star count is very low, but the methodology is dense; good for learning task sampling, private oracles, repeated runs, cost recording and trajectory auditing.
2. Project: obra/superpowers
   GitHub: [https://github.com/obra/superpowers](https://github.com/obra/superpowers)
   Stars: about 251k (as shown on the GitHub page; manual re-verification recommended)
   What it solves: packages how a coding agent works into an installable, reusable set of skills and a software development methodology, covering brainstorming, planning, TDD, subagent-driven development, code review, worktrees and other processes.
   Why it's worth a look: it reflects a trend: agent capability is moving from prompt assets to workflow, skill and methodology assets.
3. Project: ogulcancelik/herdr
   GitHub: [https://github.com/ogulcancelik/herdr](https://github.com/ogulcancelik/herdr)
   Stars: about 14.8k (as shown on the GitHub page)
   What it solves: an agent multiplexer in the terminal that shows the blocked, working and done states of multiple agents at once, detaches and reattaches long tasks, and lets agents create and read panes and coordinate waiting through a socket API.
   Why it's worth a look: once multiple agents enter real workflows, human attention becomes the bottleneck. herdr represents an "agent command center" direction: not rebuilding the chat box, but managing multiple long-running tasks, their states and handoffs.
