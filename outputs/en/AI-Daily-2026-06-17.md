# AI Daily 2026-06-17

## One-liner

> What gets an agent into production is not how clever a single answer is, but whether it has replayable evals, explainable permission governance, verifiable execution evidence and a human acceptance loop.

## Top stories

### 1. OpenAI: Predicting model behavior before release by simulating deployment
- Sources: [OpenAI blog](https://openai.com/index/deployment-simulation/)
- Type: Paper / Blog
- Rating: 5 stars
- Summary: OpenAI proposes Deployment Simulation: replay privacy-processed real historical conversations from an older model, let the new candidate model continue the answers, and predict post-launch risks in advance.

**Key points:**
1. Traditional evals easily "test hard but not like real users". Many test items are hand-built, adversarial or drawn from static question banks; they catch high-risk edges but do not necessarily predict how often something happens after a real launch.
2. The key to Deployment Simulation is not writing more questions but reusing the real task distribution. It keeps the historical conversation prefix, swaps in the candidate model to generate the follow-up answer, then uses an auditor to count new failure modes.
3. Agent scenarios are harder because tool use depends on files, network, repository state and earlier tool returns. OpenAI uses a tool simulator to approximate the real tool environment, which shows that agent evals must include the tool trajectory.

**What it means:** A more credible evaluation approach is to prepare a set of real business task samples, failure samples, tool-call logs and human judgment criteria, then run version comparisons.

**Risks and open questions:** Real business data must be de-identified; customer phone numbers, WeCom contacts, orders, contracts and keys must not go straight into the eval set.

### 2. Cursor: Governing agent autonomy with Auto-review
- Sources: [Cursor blog](https://cursor.com/blog/agent-autonomy-auto-review)
- Type: Blog
- Rating: 5 stars
- Summary: Cursor uses a lightweight classifier agent to review context before a tool call, so the agent runs automatically on low-risk actions and slows down or reroutes on high-risk ones.

**Key points:**
1. Agent permissions are not a binary choice between "fully automatic" and "approve every step". A genuinely usable product should work like a dial: low-risk actions pass automatically, and only high-risk ones trigger review or human confirmation.
2. Review cannot look only at the command itself. Whether `python script.py` is dangerous depends on the script's contents, the current directory and whether it touches keys or production data, so the classifier needs to read files, grep and look at context.
3. A good block does not immediately pop up and interrupt the person; it first feeds the reason back to the parent agent so it can choose a narrower, safer path. Only when it cannot self-correct does it ask the user to confirm.

**What it means:**
- This matters especially for customer-operations scenarios: bulk messaging, exporting customer lists, accessing the CRM, writing WeCom tags and reading keys must all have explicit permission boundaries.
- A reusable artifact: design an "agent action risk tiering table" that sorts actions into four classes, no confirmation needed, log only, second confirmation required, and forbidden.

### 3. Latent Space: The Age of Async Agents
- Sources: [Latent Space interview](https://www.latent.space/p/cognition)
- Type: Podcast / Interview
- Rating: 4 stars
- Summary: Cognition and OpenInspect discuss background agents, spec-to-PR, full VMs, memory pruning, test evidence and PMs opening PRs from Slack.

**Key points:**
1. The moat for agent products is shifting from "the model is clever" to "harness + environment + permissions + tests + collaboration interface". An agent that can really deliver needs to pull code, run the environment, test features, open PRs and respond to comments.
2. Trust in long tasks comes from evidence sent back. Screenshots, video, test logs, PR diffs and failed-retry records are worth more than a single "I'm done".
3. Memory is still hard. A long-running agent needs to remember project preferences, code structure, testing approach and past decisions, but it also has to prune regularly or old context will pollute new tasks.

**What it means:** Build an "async task agent": the user submits a request from Slack or a form, the agent executes in the background and returns a PR, a report or verifiable evidence.

**Risks and open questions:** An async agent must have human final approval, especially where customer communication, bulk messaging, data export or production changes are involved.
