### 1. Sierra: Personal Agent Protocol Poppy reaches 1.0, and Shopify turns it on for every store
- Sources: [Sierra blog](https://sierra.ai/blog/releasing-poppy); [Muse blog](https://muse.ai/blog/poppy-personal-agent-protocol); [Protocol 1.0 spec](https://personalagentprotocol.org/docs/1.0/spec); [Company implementation kit](https://personalagentprotocol.org/kit/company)
- Type: Industry
- Rating: ★★★★☆
- Summary: Sierra released version 1.0 of Poppy, the Personal Agent Protocol. A business publishes a poppy.json that tells a personal agent what it offers. Sierra says every Shopify store now publishes that file by default, and Meta's Muse already supports the protocol.
- Key figure: 100+ | design partners; Shopify publishes it for every store

**Why it matters:** Personal agents that book trips, check orders, or start returns get stuck at the door. Sites often cannot tell a customer's agent from a scraper, and block both. Existing standards already split the work: MCP covers how an agent calls tools a developer configured, OpenAPI covers existing HTTP interfaces, and Shopify's Universal Commerce Protocol (UCP) covers finding products, filling a cart, and checking out. The missing step is earlier: how an agent identifies itself at an arbitrary business and reads what it is allowed to do. Sierra writes that the protocol was announced last month with design partners including Meta, Genesys, Instinct, NiCE, Rocket, Shopify, Stripe, and Walmart, then revised over five weeks against real sites and APIs. Today is 1.0.

**Key points:**
1. A business publishes poppy.json describing how to reach it: its website, an existing API, an MCP server, or its own agent. A website-only setup can start with that file and skip customer sign-in. Authentication is OAuth, and the customer can manage the agent's permissions. The protocol can be adopted in stages, and industry extensions do not change the core. Shopify and Sierra co-authored the commerce extension that links Poppy and UCP.
2. Sierra says every Shopify store already supports UCP by default and now also publishes a Poppy file automatically, with no extra work for the merchant. UCP handles the shopping itself. Poppy handles the agent arriving, identifying itself, and learning its permissions. The commerce extension lets an agent shop as a guest or sign in with the customer's account, and requires the agent to ask the customer before certain actions. It also connects to UCP Ask, so the shopper's agent can talk to the store's agent. Sierra writes that Shopify's businesses span more than 175 countries.
3. Sierra says Poppy is on for everyone who uses Muse, and that Muse looks for Poppy first on every site it visits. Muse's own post says it is the first personal agent to support the protocol, and that any business can implement it today. Sixty new design partners bring the total to more than 100. Sierra says Mercury and Turkish Airlines already let a personal agent handle tasks; in the same section, Synchrony is described as going to bring financing and rewards into agent-led shopping.

**What it means:** On this line, MCP first answered how an agent calls tools someone configured, and UCP then answered the shopping actions themselves. Poppy fills in arrival and authorization. Version 1.0 plus Shopify's default file means a personal agent does not need a separate scraper-style integration for every store. The next limit is less likely to be whether the file exists, and more likely to be whether the business will let the agent actually place an order or move money: the extension says some actions require asking the customer first, but each store's approval policy stays with the store. Other personal agents that want into the same stores will read the same poppy.json instead of inventing another handshake.

**Risks and open questions:** "On for every store," "Muse looks for Poppy first," and "more than 100 design partners" come from Sierra's post. That post was not cross-checked against Shopify's own docs. Muse's post confirms that Muse supports 1.0 and does not repeat the claim that it looks for Poppy on every site. What a named partner can do today, such as checking a balance or booking a flight, is that partner's scenario, not a promise that the protocol completes payment everywhere. The 1.0 text on personalagentprotocol.org is the spec.

### 2. Google: Antigravity adds Dynamic Workflows, scheduling sub-agents with a Python script
- Sources: [Dynamic Workflows docs](https://antigravity.google/docs/dynamic-workflows); [Changelog](https://antigravity.google/docs/changelog); [November 11 /swarm docs](https://antigravity.google/docs/swarm); [August 27 /teamwork post](https://antigravity.google/blog/teamwork-when-ai-becomes-a-research-partner)
- Type: Product update
- Rating: ★★★★☆
- Summary: Google Antigravity adds /run-workflow in the app and the CLI. The agent writes and runs a Python script that schedules sub-agents in parallel or in sequence. The docs say it is available on Google AI Pro and Ultra.
- Image: ![A /run-workflow enters a Discover phase that lists modules, then a Review phase that checks files in parallel](images/2026-11-15/2-antigravity-workflow.png) (Image: Google)

**Why it matters:** Coding agents already have several ways to split work, and the control flow still mostly lives in the conversation. On November 11 Antigravity previewed /swarm: the current conversation coordinates, and workers collaborate on a shared message board. The November 12 changelog paired Orchestrator with Gemini 4 Hydrogen: in one conversation, Gemini 4 Carbon or Argon plans and reviews, and routine tool calls go to Hydrogen. The August 27 /teamwork post is a collaborative team that starts with a scoping interview. Those designs keep order inside the model's context. Dynamic Workflows writes the order as code. The agent drafts a short Python script for the task, runs agents concurrently with parallel() or in order with pipeline(), and has each sub-agent return a result that matches a JSON Schema. File reads and test logs stay out of the main conversation.

**Key points:**
1. The command is /run-workflow. The docs say Google AI Pro and Google AI Ultra can use it in the app and the CLI. The changelog records the feature in Antigravity App v2.32.0, dated November 13, 2026. The runtime includes its own Python, so the user does not install Python separately.
2. The script runs in its own process. Unless the permission preset already allows it, the user approves each script before it runs. Approval covers that exact script; a command-prefix rule cannot cover a Python script. Each agent the workflow starts still follows the user's permission preset and asks in its own conversation.
3. The docs put the options in one table. Orchestrator is planning versus execution inside a single conversation. Sub-agents fit handing off one task. /swarm fits agents that need to look at each other's diffs and agree on interfaces. /teamwork fits a multi-milestone project that starts with a scoping interview. If agents need to coordinate with each other while they work, the docs say to use /swarm, not a workflow.

**What it means:** /swarm answers "several agents negotiate on one board." Orchestrator answers "who plans and who acts inside one conversation." /run-workflow is the third shape: the same check across many files, or a failing test written before the fix, with the control flow in a script a person can review instead of in a conversation that keeps growing. The docs draw that boundary themselves, so Google is not treating one orchestrator as a replacement for the others. If other coding agents follow, the next step is more likely a plan the user reads as code before it runs, not only another multi-agent switch.

**Risks and open questions:** The changelog dates the feature to v2.32.0 on November 13, and the docs say Pro and Ultra can use it, but they do not say every install receives that build at the same moment. Agents started in parallel each ask for permission, so one fan-out can become many prompts. Nothing independent shows that scripted orchestration drifts less than /swarm.

### 3. Vercel: Token Pass stays $30 a month, and the included tokens rise from $80 to $150
- Sources: [Vercel changelog](https://vercel.com/changelog/vercel-token-pass-now-includes-one-hundred-fifty-dollars-of-monthly-tokens)
- Type: Product update
- Rating: ★★★★☆
- Summary: Vercel Token Pass remains $30 per team per month. The included token value rises from $80 to $150, for five open-weight models on AI Gateway. When the credit runs out, Token Pass-scoped keys stop and do not incur overage.
- Key figure: $150 | included tokens per month; the price stays $30

**Why it matters:** The Kimi, Zhipu GLM, and DeepSeek APIs can already be called by usage. What a gateway is competing for is whether developers will fold those bills into one monthly fee. Vercel's Token Pass is not a product created today. The changelog keeps the same tier, $30 per team per month, and changes the included amount from $80 to $150. The credit applies to open-weight models on AI Gateway. The post names Kimi K3, Kimi K3.1 Pro, GLM 5.3, GLM 5.3 Flash, and DeepSeek V4.1 Flash.

**Key points:**
1. Credit resets each billing period and does not roll over. After it runs out, requests that use a standard AI Gateway key or an OIDC token fall back to the team's AI Gateway balance. Requests that use a Token Pass-scoped key stop, with no overage charges.
2. Token Pass is an Early Access add-on for Pro teams, with limited spots and a waitlist when they fill. To connect an agent, run vercel token-pass in the Vercel CLI, or use a Token Pass API key when the agent supports AI Gateway.
3. The changelog timestamp is 2026-11-13 22:24 UTC, and the page is labeled 13 Nov 2026. The model list does not add a vendor. What changed is the amount included in the same monthly fee.

**What it means:** Pay-as-you-go APIs for these five models were already there, and the previous Token Pass tier already wrapped $80 of credit in a $30 fee. Today changes the size of the bundle, not the models. At the gateway layer, the difference is becoming how much monthly credit is included, and whether requests stop when that credit ends. A team that wants a hard ceiling uses a scoped key, and requests stop. A team that wants the work to continue uses a standard key, and the overage lands on a separate Gateway balance. Putting both keys in one changelog entry means Vercel leaves the overage risk on the key type instead of deciding it for every user.

**Risks and open questions:** Early Access, limited spots, and a waitlist mean not every Pro team can subscribe today. The $150 is the token value stated in the changelog, not a new unit price from each model's own pricing page; this post does not restate those prices. Unused credit does not roll over.
