# AI Daily 2026-06-24

## One-liner

> Agent products are moving from "one-off chat" to "resident team member + long-cycle work loop + reusable evaluation assets". The core skill of an AI product manager / FDE is not writing fancier prompts but designing context, permissions, tools, memory, human confirmation, traces and evals so the agent is controllable, traceable and reviewable in real business.

## Top stories

### 1. Anthropic: Introducing Claude Tag
- Sources: [Anthropic blog](https://www.anthropic.com/news/introducing-claude-tag)
- Type: Official blog / Agent product form
- Rating: ★★★★★
- Summary: Claude Tag moves the agent from a personal chat window into a Slack channel as a "team collaborator"; the key capabilities are channel-scoped context, memory, tools, async work and permission auditing.

**Why it matters:** This is not a simple Slack bot but a clear demonstration of what an enterprise agent product looks like. Claude can be authorized into specified channels, connected to specified tools and codebases, remember channel-relevant information, and execute tasks asynchronously after being @-mentioned. Anthropic also mentions that a large share of its internal product teams' code was created by an internal version of Claude Tag, which shows team-level agents moving from "personal productivity tool" to "node in the organization's workflow".

**Key points:**
1. Agents need "context shared by many people". With Claude in a channel, team members can pick up the conversation without each person explaining the background from scratch.
2. Memory must be isolated by channel and purpose. Claude in sales, engineering and support roles should have different tool, data and memory boundaries.
3. Async and ambient behavior is the next step. The agent does not only answer passively; it can follow up on silent threads, surface relevant information and schedule future tasks, but it must be constrained by permissions and logs.

**What it means:** WeCom scenarios can borrow this form, but more conservatively. Rather than one "all-purpose WeCom bot", build several channel-scoped / role-scoped agents, such as a customer-operations assistant, an after-sales follow-up assistant and a content QA assistant. For each agent, define separately which customer data it can see, which tools it can call, which fields it can write back and which bulk-messaging actions it can trigger.

**Risks and open questions:** Read the full post online. Do not connect real customer chats, phone numbers, orders, contracts, WeCom contacts or internal screenshots to a demo; proactive reminders and async follow-ups easily cause mistaken outreach, so bulk sends, database writes and external link sending must default to human confirmation. Administrators also need to watch token spend, log visibility and memory isolation between channels.

### 2. OpenAI: Codex-maxxing for long-running work
- Sources: [OpenAI page](https://openai.com/index/codex-maxxing-long-running-work/); [Official PDF](https://cdn.openai.com/pdf/8a9f00cf-d379-4e20-b06f-dd7ba5196a11/OAI_WhitePaper_Codex-maxxing26.pdf)
- Type: Official white paper / Workflow / Loop engineering
- Rating: ★★★★★
- Summary: This white paper describes Codex as a long-term workspace rather than a one-off coding assistant; the core is durable threads, steering, memory, tools, thread automations and verifiable goals.

**Why it matters:** The competitiveness of an AI PM / FDE will increasingly look like a "workflow designer". A single prompt can produce content, but the real leverage comes from making tasks persistent, reviewable, hand-off-able and verifiable.

**Key points:**
1. A durable thread is the work container. Important projects need a place to come back to, where past decisions, preferences, open questions and next actions keep accumulating.
2. Memory must be openable, editable and diffable. Do not let long-term memory hide silently in chat history; it should settle into reviewable assets such as people, projects, decisions and loop-closure status.
3. Strong goals must be verifiable. A good task is not "implement according to plan" but gives tests, acceptance criteria, constraints and a definition of done, so the agent knows when it is actually finished.

**What it means:** This maps directly onto the AI Daily automation the author is building. Instead of opening a new prompt every day, let the agent run continuously carrying memory, source conventions, download rules, public-risk checks and the git upload process. A future WeCom customer-operations agent should likewise define the loop first: capture signals, generate drafts, check links, intercept private data, confirm by hand, record results.

**Risks and open questions:** The PDF has been downloaded, about 3.56 MB locally with a `%PDF` header, but it should still be opened and checked by hand. Long-lived threads and memory easily accumulate sensitive data, especially with connectors such as Slack, Gmail, Chrome, WeCom and CRM; any outbound email, bulk message, customer-data export or database write must keep a human confirmation point.

### 3. arXiv: Human-on-the-Bridge — Scalable Evaluation for AI Agents
- Sources: [arXiv abstract](https://arxiv.org/abs/2606.16871); [arXiv PDF](https://arxiv.org/pdf/2606.16871)
- Type: Paper / Evaluation / Agent harness
- Rating: ★★★★★
- Summary: Human-on-the-Bridge argues that agent evaluation should assess the "behavioral system", front-loading human expert judgment as reusable evaluation assets, with a harness then running multi-turn adversarial tests, trace capture, multi-juror scoring and evidence-linked reports.

**Why it matters:** Many teams still evaluate agents by "does the final answer look right", but real agent failures often happen in the trajectory: claiming to call a tool without calling it, skipping required tools, policy drift, being talked by the user into rewriting rules, refusing safely without solving the problem. HOB's value is upgrading human judgment from manual review every time to repeatably runnable evaluation intelligence.

**Key points:**
1. Agent evaluation is not single-turn answer scoring but behavioral, procedural, adversarial, evidence-linked assessment.
2. HOB's reusable assets include domain context, Red-Team Traps, Juror Personas, scoring guidelines, audit rules and fallback policies.
3. The paper reports coverage of 23,500 agent turns, exposing phantom tool calls, missing mandatory tool calls, policy drift and manipulation paths that static benchmarks easily miss.

**What it means:** For a WeCom customer-operations agent, do not only ask "does the reply sound nice"; also check whether it read the right customer context, skipped privacy checks, wrongly promised a discount, sent an unconfirmed link, or wrote customer data somewhere it should not.

**Risks and open questions:** This is an arXiv preprint that needs further verification and cannot be taken as an industry conclusion; the associated open-source harness currently has very few stars, so its engineering maturity must be assessed separately. Evaluation samples must not contain real customer data, medical records, financials, contracts, phone numbers or internal keys; do not take adversarial samples straight into production groups to test either.

## Open source worth a look

1. Project: ProofAgent-ai/proofagent-harness
   GitHub: [ProofAgent-ai/proofagent-harness](https://github.com/ProofAgent-ai/proofagent-harness)
   Stars: 5 (GitHub API, verified 2026-06-24)
   What it solves: a pytest-like multi-turn adversarial evaluation harness for AI agents, with a juror panel, production-critical metrics, traces, reports and CI.
   Why it's worth a look: the star count is very low and its engineering maturity needs further checking, but it is closely tied to the HOB paper's methodology and is good for learning "how to structure agent evaluation assets".
2. Project: headroomlabs-ai/headroom
   GitHub: [headroomlabs-ai/headroom](https://github.com/headroomlabs-ai/headroom)
   Stars: 48,579 (GitHub API, verified 2026-06-24)
   What it solves: compresses tool outputs, logs, files, RAG chunks and conversation history, offering a library, proxy, MCP server and cross-agent memory, with the goal of reducing context cost.
   Why it's worth a look: the pain point of context engineering is getting clearer; an agent is not better the more context you stuff in, it needs to filter, compress and be able to retrieve the original.
3. Project: upstash/context7
   GitHub: [upstash/context7](https://github.com/upstash/context7)
   Stars: 57,936 (GitHub API, verified 2026-06-24)
   What it solves: puts up-to-date, version-specific library documentation into LLM context via CLI / MCP, reducing outdated and hallucinated APIs in AI coding.
   Why it's worth a look: FDEs doing demos and deliveries often get stuck on SDK versions, auth APIs and framework upgrades; Context7 represents a very practical "external documentation injection" pattern.
