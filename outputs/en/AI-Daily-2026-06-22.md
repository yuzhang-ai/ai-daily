# AI Daily 2026-06-22

## One-liner

> Agent competitiveness is shifting from "how well the model answers" to "whether a real workflow can be discovered, authorized, simulated, evaluated, audited and accepted by a human". The core value of an AI PM / FDE is turning business scenarios into a reusable capability catalog, an eval harness and a safe release process.

## Top stories

### 1. OpenAI: Predicting model behavior before release by simulating deployment
- Sources: [OpenAI blog](https://openai.com/index/deployment-simulation/); [Official PDF](https://cdn.openai.com/pdf/predicting-llm-safety-before-release-by-simulating-deployment.pdf)
- Type: Paper / Official blog
- Rating: ★★★★★
- Summary: OpenAI proposes Deployment Simulation, replaying de-identified real conversation prefixes through a candidate model to predict post-launch misbehavior, eval awareness and tool-call risk in advance.

**Why it matters:** The hardest part of an agent product is not the demo but whether it stays stable after launch under real traffic, real tools and real permissions. This method moves evals from "write questions to examine the model" to "simulate the real deployment distribution", a useful reference for FDEs validating customer scenarios.

**Key points:**
1. Traditional evals tend to have narrow coverage and biased samples, and get recognized by the model as tests; Deployment Simulation uses real-distribution prefixes to reduce these problems.
2. OpenAI ran experiments on about 1.3 million de-identified conversations and validated prediction quality with taxonomy coverage, directional accuracy and rate calibration.
3. The hard part of simulating agentic tool use is external state and the realism of read/write tools; the paper states clearly that it is a complement, not a replacement for red teaming, adversarial evals and tail-risk analysis.

**What it means:** When building enterprise agents, do not just write 20 ideal prompts; sample real but de-identified tickets, WeCom SOPs and customer-operations tasks, replay the candidate model and record failure rate, tendency to overstep permissions, hallucination and tool misuse.

**Risks and open questions:** Production data must be de-identified and authorization confirmed first; do not upload customer names, phone numbers, WeCom chats, contracts, orders or keys; tool simulation must not connect directly to production systems, use a sandbox or mocks first.

### 2. Google: ARD + A2A are filling in the discovery, trust and collaboration layers of the agentic web
- Sources: [Agentic Resource Discovery](https://developers.googleblog.com/announcing-the-agentic-resource-discovery-specification/); [A2A collaborative agents](https://developers.googleblog.com/how-a2a-is-building-a-world-of-collaborative-agents/); [A2UI](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/)
- Type: Official blog / Open specification
- Rating: ★★★★★
- Summary: Google splits the agent ecosystem into three layers: ARD handles capability discovery, A2A handles agent-to-agent collaboration, and A2UI handles cross-surface generative UI.

**Why it matters:** Agent products are moving from single-point tool calls to collaboration networks that cross organizations, protocols and permission boundaries. What an FDE delivers in future is not "a bot" but a discoverable, verifiable, governable capability catalog.

**Key points:**
1. ARD uses domain-hosted catalogs and a federated registry so agents can find capabilities such as MCP servers, A2A agents and OpenAPI tools, with trust metadata attached.
2. A2A stresses secure boundaries and zero context pollution: sensitive processes stay inside a dedicated agent and the main agent only receives results, reducing context pollution and data exposure.
3. A2UI moves the UI an agent returns from plain text to portable component blueprints, suited to multi-agent, multi-frontend, multi-enterprise-system collaboration.

**What it means:** Enterprise agent solutions should start designing "capability catalog + permission boundaries + audit records" rather than stuffing every tool into one all-purpose prompt. In WeCom customer operations especially, tags, bulk messaging, CRM, knowledge base and tickets should be split into controllable capabilities.

**Risks and open questions:** Capability discovery is not automatic authorization; cross-agent calls must guard against prompt injection, unauthorized reads, wrong bulk sends and wrong database writes; the catalog must not expose internal API keys or customer data samples.

### 3. Dwarkesh: The data black hole at the center of AI
- Sources: [Dwarkesh Podcast / Essay](https://www.dwarkesh.com/p/the-sample-efficiency-black-hole)
- Type: Long-form essay / Interview follow-up
- Rating: ★★★★☆
- Summary: Dwarkesh uses sample efficiency to explain the limits of current models: AI can bring common white-collar tasks into distribution through massive training, but does not necessarily have human-style fast learning yet.

**Why it matters:** This helps AI PMs judge which processes are suited to automation and which still need a human expert as backstop.

**Key points:**
1. Recent capability gains look more like expanding and improving the training data distribution than solving human-level sample efficiency.
2. Common white-collar tasks can enter the model's distribution through RL, SFT, verifiers and synthetic data, so there is still large commercial value.
3. What is genuinely scarce is out-of-distribution judgment, intent selection, problem definition and continual learning, which still require experts and organizational processes.

**What it means:** When picking scenarios, prioritize tasks that are "high-frequency, verifiable, reusable, low privacy exposure", such as customer segmentation, campaign retrospectives, knowledge-base Q&A and follow-up reminders; be cautious about promising full automation of low-frequency complex decisions.

**Risks and open questions:** The essay/interview needs to be read or listened to in full online; this is a personal judgment, not an official research conclusion. When citing it, do not stretch "sample efficiency is still the bottleneck" into "AI automation has no value".

## Open source worth a look

   GitHub: [ChromeDevTools/chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp)
